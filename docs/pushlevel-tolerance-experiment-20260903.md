# 推关服务器容差探测实验记录（2026-09-03）

> 目的：验证服务器对 `fight_endlevel` 提交战报的验算严格程度 —— 能否在官方真实胜利结果基础上微调战绩数值，重算 `outputCode` 后仍被服务器接受。

## 1. 实验环境

- 账号：80号战士（9780服，roleId 647473183），战斗可胜，起始约 2049 关

- 基底：官方无头引擎生成的**真实胜利结果**

- 方法：每轮独立 headless iframe（单场/单提上限），对战绩字段做**单点微调**，保持 `levelId`、`battleTime`、`tapTimes`/`autoTapTimes` 为官方原值，重算 MD5 `outputCode` 后提交 `fight_endlevel`

## 2. 判定依据

- 服务器返回 `Fight_EndLevelResp` body **395 字节** = 成功响应

- 失败 / 拒绝为 **106 字节**

- `ROLE.levelId` 持续推进 = 该关被接受

## 3. 5 轮实验结果

| 轮 | 微调内容                               | 提交关卡 | 服务器判定 |
| - | ---------------------------------- | ---- | ----- |
| 1 | 我方主力 HP 276845688 → 276845687（-1）  | 2049 | 接受，推进 |
| 2 | 我方主力 HP → 226845688（-5000万，约 -18%） | 2067 | 接受，推进 |
| 3 | 我方主力 HP → 0（全扣光）                   | 2076 | 接受，推进 |
| 4 | 我方主力 rage → 0                      | 2097 | 接受，推进 |
| 5 | 我方主力 damage +1亿                    | 2108 | 接受，推进 |

## 4. 结论（已验证事实）

服务器对 `fight_endlevel` 提交的战报中 **sponsor HP、rage、damage 等战绩字段不做数值/守恒重放校验**：

- 即使 HP 扣到 0、怒气清零、伤害凭空加 1亿，只要 `outputCode` 与提交内容自洽（MD5 公式正确），服务器就接受并推进关卡。

这推翻了此前"服务器会重新模拟战斗验算"的假设。服务器校验的核心是 **outputCode 公式自洽性**（以及 levelId 等必需字段完整），而非战绩数值真实性。

## 5. 推论（合理推断）

- 只要持有官方引擎生成的真实战斗结果作为"骨架"（保证字段类型、键序、种子等格式正确），单点篡改战绩数值是安全的。

- 此前 9070 关"伪造胜利"失败（800080）的真正原因**不是数值被重放校验**，而更可能是：直接把失败结果的 `isWin` 改 true 但保留"我方全灭/hp=0、敌方存活"的矛盾形态，外加缺失 levelId 等字段问题（200020）。

- 后续实现可基于"真实结果 + 自洽哈希"自由调整战绩展示数值。

## 8. 成功 / 失败差异分析（9070 失败 vs 80号战士成功）

### 8.1 一句话核心

**80号战士成功**：基底是官方引擎生成的**真实胜利结果**，只篡改展示数值 -> 服务器接受。
**9070（130301444，level 9070）失败**：基底是**真实失败结果**，需要手动"伪造胜利" -> 服务器拒绝。
问题不在"数值验算"，而在"结果形态自洽性"。

### 8.2 9070 为什么失败

该角色在 9070 关战斗**真实失败**，实验要把它改判为胜利，两条路径都失败：

1. **只改 isWin + 重算哈希**（iswin-only）：提交的战报是"我方全灭（hp=0、ext.curHP=0）+ 敌方存活 + isWin=true"——**形态矛盾**（胜利但团灭），服务器一眼看穿 -> 800080。
2. **successify 翻正**（我方存活+怒气满、敌方全灭、伤害守恒补齐）：虽然形态上"看起来像胜利"，但仍失败 -> 800080。

关键点：**successify 是纯本地猜测的胜利形态**，无法 100% 复刻官方胜利结果的所有内部一致性细节（单成员 hp+takeDamage 守恒、sponsor.damage 总量 == accept.takeDamage 总量、ext.curHP == 各成员hp之和、rage/energy/治疗值细节等），服务器在更细的守恒校验中抓到破绽。

### 8.3 80号战士为什么成功

80号战士（9780服）在 2049 关战斗**真实胜利**，官方引擎生成的就是胜利结果——**根本不需要伪造胜利**。实验只是在这个真实胜利骨架上篡改单个数值（HP -1/-5000万/->0、rage ->0、damage +1亿），全部被接受。

因为骨架（accept 全灭、sponsor 存活、ext.curHP 非 0、rage/damage 守恒）**全部保持官方原值自洽**，只有被篡改的那一处数值变了，其他约束仍然成立，所以服务器放行。

### 8.4 差异对照表

| 维度    | 9070（失败）             | 80号战士（成功）  |
| ----- | -------------------- | ---------- |
| 基底    | 真实失败结果               | 真实胜利结果     |
| 需要做的事 | 伪造胜利（改 isWin + 翻正战绩） | 仅篡改展示数值    |
| 战报形态  | 团灭+敌方存活 或 手工翻正       | 官方原生胜利形态   |
| 内部守恒  | 矛盾 或 手工猜测不精确         | 官方引擎保证精确自洽 |
| 结果    | 800080 拒绝            | 全部接受       |

### 8.5 服务器校验程度（三层）

1. **必需字段完整**（必查）-> 缺 levelId 报 200020。
2. **outputCode 公式自洽**（必查）-> MD5 与提交内容不符即拒绝。
3. **结果形态自洽性**（会查）-> isWin 与双方存活/团灭、ext.curHP、伤害守恒等**整场战报的内在一致性**；对"伪造胜利"这类形态矛盾/翻正不彻底的战报会拒绝。

**明确不做的**：不做"数值级重放验算"——不逐帧模拟战斗、不校验战绩数值是否等于某场真实模拟的结果（容差探测已证明 HP/rage/damage 可随意篡改）。

## **一句话总结**：服务器是"**形态裁判**"不是"**重放裁判**"——它验"这战报像不像一场自洽的胜利"，不验"这场战斗数值真不真"。拿到官方真实胜利结果当骨架，改数值安全；但想凭空把失败翻成胜利，就得把整场战报做到内部完全自洽，手工合成很难满足所有守恒约束。
