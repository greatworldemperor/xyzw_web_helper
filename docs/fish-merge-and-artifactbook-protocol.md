## 1. 数据模型

### 1.1 itemId 编码（5 位）

```
itemId = T T S S L
         │ │ │ │ └── 等级 1..5（最高 5 级）
         │ │ └────── 品种序号（01..12）
         └────────── 档位前缀
```

观察到的 4 个档位前缀：`13` / `14` / `15` / `16`（另有历史遗留 `1118`，artifactBooks 里 artifactId=11185、claimedStar=5）。

图鉴分组 id = 前 4 位（去掉等级位）。例：itemId `14121` → 品种 `1412` → 图鉴 key `"1412"`；`14121/14122/14123/14124/14125` 分别是同一条鱼的 1~5 级。

⚠️ 别按「15xxx 都是鱼」去扫库存：`15001`(68900)、`15002`(1502) 是货币类道具（数量级不像鱼）。鱼/神器的数量都是个位数~二十几。判据：能从 `role.artifactBooks` 里找到 `<前4位>` key。

### 1.2 role.artifactBooks 结构

```jsonc
"artifactBooks": {
  "1302": { "artifactId": 13025, "claimedStar": 1 },
  "1118": { "artifactId": 11185, "claimedStar": 5 }
}
```

- `artifactId`：**历史最高解锁等级**（= 该品种曾经拥有过的最高等级 itemId）。即使那条鱼后来被合并吃掉，这里仍保留 → 可以据此判断「升到 N 级」是否达成过。
- 只在**刷新最高纪录**时才出现在 SyncResp 里；合成出更低等级的鱼时，SyncResp 不带 artifactBooks。
- `claimedStar`：**已点亮（已领取）星级**，初始都是 1（拥有 1 级即算解锁 1 星）。

### 1.3 role.book

```jsonc
"book": { "bookPoint": 2135, "bookLastReward": 43, "bookValue": 0, "bookStageId": 0, ... }
```

- `bookPoint`：累计图鉴点数（只增，不因为领奖而扣——实测领奖响应里没出现 bookPoint 变更）
- `bookLastReward`：已领到的点数奖励档位序号

## 2. 合并鱼：`artifact_upgradestar`

### 2.1 请求 / 响应

```jsonc
// SEND  104 字节，scheme=x
{ "ack": <n>, "body": { "heroId": -1, "itemId": 13022 }, "time": ..., "seq": 43, "cmd": "artifact_upgradestar" }
```

- `heroId: -1` = 从**背包**取鱼（不是从武将身上卸）。本次 120 次合并全是 -1。
- `itemId` = **当前要升级的那条鱼的 id**（即「本级」），不是目标等级 id。

```jsonc
// RECV（不是 Artifact_UpgradeStarResp，而是通用 SyncResp，靠 resp=请求seq 匹配）
{
  "seq": 45, "ack": 44, "time": ..., "resp": 45, "cmd": "SyncResp",
  "body": { "role": {
      "items": { "13021": {"quantity": 7}, "13022": null, "13023": {"itemId":13023,"quantity":1,"ext":null} },
      "artifactBooks": { "1302": { "artifactId": 13023 } }
  } }

```

- `items.<id>: null` = 该道具归零/消失；只回传**发生变化的**条目。
- 项目 `_handlePromiseResponse` 走 `resp` 序号匹配（第 1030 行），所以「请求 cmd ≠ 响应 cmd」不用额外注册映射。

### 2.2 消耗规则（本次全量重放 120 次，零例外）

记该档位的 **k = 每升一级额外吃掉的 1 级鱼条数**，实测：

| 前缀 | k | 1→2 消耗 | 2→3 / 3→4 / 4→5 消耗 | master 的说法 |
| --- | --- | --- | --- | --- |
| 13xx | **1** | 2 条 1 级 | 本级鱼 ×1 + 1 级鱼 ×1 | 红色鱼 ✓（3 级 = 3 条） |
| 14xx | **2** | 3 条 1 级 | 本级鱼 ×1 + 1 级鱼 ×2 | 橙色鱼 ✓（3 级 = 5 条） |
| 15xx | **5** | 6 条 1 级 | 本级鱼 ×1 + 1 级鱼 ×5 | 蓝色鱼 ✓（3 级 = 11 条） |
| 16xx | **20** | 21 条 1 级 | 本级鱼 ×1 + 1 级鱼 ×20 | (本次额外发现的第 4 档) |

一句话：**「升 L(n)→L(n+1) = 消耗本级鱼 1 条 + 同品种 1 级鱼 k 条」，n≥2 时如此；n=1 时本级就是 1 级鱼，所以合计消耗 k+1 条 1 级鱼。**

等价的「总投入」口径（master 的模型），一条 L 级鱼总共吃掉的 1 级鱼：

```
V(L) = 1 + (L - 1) * k
V(1)=1  V(2)=1+k  V(3)=1+2k  V(4)=1+3k  V(5)=1+4k
```

与抓包完全吻合：

- 13xx (k=1)：V(5)=5 条。1302 起始 10 条 → 最后合成 2 条 5 级（#17 一条、#25 一条），10 条刚好用完 ✓
- 14xx (k=2)：V(5)=9 条。1401 起始 21 条 → 合成 2 条 5 级（9+9）+ 余 3 条合成 1 条 2 级（V(2)=3），21 条用完 ✓
- 15xx (k=5)：1501 起始 15 → 1 次 1→2（-6）、1 次 2→3（-5），余 4 条不够下一次 ✓
- 16xx (k=20)：1601 起始 80 → -21、-20、-20 后余 19 条停手 ✓

⚠️ 材料是**服务端自动挑的**，请求里没法指定。实测服务端只吃 1 级鱼，不会误吃更高等级的成品（1401 第二次升级 `.14012` 时，仓库里还躺着一条 5 级 `14015`，没被动用）。

## 3. 图鉴点亮：`book_batchupgrade`

### 3.1 请求 / 响应

```jsonc
// SEND 110 字节（复读 4 次即可从 1 星点到 5 星）
{ "body": { "club": 0, "isArtifact": true, "isSkin": false }, "cmd": "book_batchupgrade" }

// RECV Book_BatchUpgradeResp
{ "cmd": "Book_BatchUpgradeResp", "resp": <请求seq>,
  "body": { "role": {
     "book": { "bookPoint": 2203 },
     "artifactBooks": { "1301": {"claimedStar":2}, "1302": {"claimedStar":2}, ... }
  } } }
```

### 3.2 行为

- **一次调用只推进 1 星**，但**所有符合的品种一起推进**（batch 的含义在这）。
- 推进条件（实测推断）：该品种 `artifactId` 的等级 ≥ 目标星数。
  - 第 1 次调用 → 26 个品种到 2 星（连只合到 L2 的 1301/1505/1506 都在）
  - 第 2 次 → 23 个到 3 星（1301 掉队，因为它只有 L2）
  - 第 3 次 → 19 个到 4 星
  - 第 4 次 → 15 个到 5 星
- 点数增量（bookPoint）：2135 →2203(+68) →2263(+60) →2313(+50) →2355(+42)
  - **点数公式没能反解**：按「每品种每星固定分」或「档位 × 星数」拟合都出非整数（14xx 解出 2.75、16xx 解出 1.75），说明每档甚至每个品种的分值是独立配置。建议：实现时**不要本地预测 bookPoint**，直接读响应的 `role.book.bookPoint`。
- 建议实现：无脑连发 4 次，每次用响应里的 claimedStar 判断是否还在变化；变了继续，没变就停。

## 5. 可直接抄进代码的规则表

```js
// 每升一级额外消耗的 1 级鱼数量（= V(L)=1+(L-1)*k 里的 k）
export const FISH_LEVEL_COST = { 13: 1, 14: 2, 15: 5, 16: 20 };

// 合成一条 L 级鱼，总共需要多少条 1 级鱼
export const totalCost = (tier, level) => 1 + (level - 1) * FISH_LEVEL_COST[tier];

// 单次请求会吃掉：本级鱼 1 条 + 1 级鱼 k 条（level=1 时本级即 1 级，合计 k+1）
export const upgradeCost = (tier, level) => ({
  self: 1,
  lv1: FISH_LEVEL_COST[tier],
});
```

## 6. 切换阵容会触发服务端自动合并（`fish_auto_merge.jsonl`，2026-09-30 16:42，海王 @ 26501 服）

master 问题：「切换第二阵容时没合并的鱼自动升级了——是有专门的一键合并指令，还是客户端自己模拟了合并？」

**答案：都没有。是服务端在 `presetteam_saveteam`（启用某套阵容）的 handler 里原子完成的。**

证据链（37 帧，复现验证 17/17 精确）：

1. 全程 **0 次 `artifact_upgradestar`**；那个 `(无 cmd)` SEND 帧只是 1 字节明文心跳。
2. 切换请求就一帧：`presetteam_saveteam { teamId: 2 }`（90 字节，useTeamId 1→2）。
3. `PresetTeam_SaveTeamResp`（10.7KB）里直接带着 `role.items` 大增量——**19 种鱼归零、11 种新产出、18 个品种被动过**：
   - 归零：`13011/13013/13021/13031/13041/13051/14011/14023/14031/14043/14051/14063/14071/14091/14111/14113/14122/15062/16012 → null`
   - 新产出：`13022/13043/13053/14034/14042/14062/14093/14114/14123/15063/16013`（`{itemId,quantity,ext}` 形态）
   - 数量更新：`13015→2、13035→3、14015→8、14025→6、14034?…14125→7、15061→2、16011→1` 等
4. **消耗规则与手工合并完全一致**（k=1/2/5/20 的铁证）：
   - `16011: 21→1`（恰 −20）+ `16012→null` + `16013 新建` = 一步 k=20 的 `16012→16013`
   - `14021: 5→1`（−4 = `14023→14024`、`14024→14025` 两步 ×2）+ `14023→null` + `14025→6`
5. **换阵释放回背包的鱼也直接被吃进合并**：阵容1 英雄 116 身上的 `16012` 切阵后回包，随即被合成了 `16013`——同一个响应里完成「卸下→合并」，只能是服务端行为。
6. 合并范围**不止新阵容需要的**：阵容2 只需要 `13045×2 / 13055×2 / 11155`，但 1301/1302/1303/1401~1412/1506/16xx 全动了 ⇒ 语义是「**把背包里所有能往上合的鱼都合到材料不够为止**」，新阵容要的等级顺带被填满（这才叫"没有合并的鱼自动合并升级"）。
7. 响应里**没有 `artifactBooks` / `book` 增量**（grep 0 命中）：要么该号图鉴早已解锁到同等阶，要么服务端自动合并不计图鉴 ⇒ **切阵后图鉴点亮仍需自己补 `book_batchupgrade`**，不能指望切阵代劳。
8. 合并完成后客户端立刻连发 3 次 `fight_startlevel`（推关页拿新阵容继续打）。

### 对自动化的启示

- 想"一键合并"有两条路：① 自己按 §2.3 的 k 表算链、逐条发 `artifact_upgradestar`（可控、不切阵）；② 发一帧 `presetteam_saveteam {teamId}` 借服务端的手（一帧合完全背包，**副作用 = 会真的切换阵容**）。
- ⚠️ preset 模板里的 `artifactId` 只是快照：16012 已被合成 16013，模板里英雄 116 仍记着 16012——按模板校验"鱼还在不在"会误判，要以 `role.items` 实时为准。
- 若走 ② 路线，响应 `resp` 匹配 seq 即可；items 增量直接当结果读，不用自己算。
