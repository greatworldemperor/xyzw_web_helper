# 7.7.12.js：skip150 关卡配置 Hook 逆向记录

> 研究日期：2026-09-04
>
> 目标：分析 [scripts/7.7.12.js](../../scripts/7.7.12.js) 中与“自动推 150 关”有关的混淆代码，确认它的实际算法、注入点、边界和与主线 pushLevel 协议的关系。
>
> 本文只记录本地静态分析和隔离运行时实验。研究过程中没有读取或使用真实 BIN，没有登录真实角色，没有向游戏服务器发送请求，也没有修改 `scripts/7.7.12.js`。

## 1. 先给结论

脚本中的“自动推 150 关”由 `skip150` 功能实现。它不是当前仓库里的 `outputCode` 合成器，也不是直接循环发送 150 次 `fight_endlevel`。

它的核心算法是：

```js
if (skip150Enabled && 2 <= levelId && levelId <= 150) {
  return {
    ...originalLevelConfig,
    monsters: [[[0]]],
  };
}
```

具体执行方式：

1. 脚本初始化一个名为 `o3` 的控制器。
2. 从 `localStorage["skip150_enabled"]` 读取开关。
3. 开关启用后，通过 `window.__require("Configs")` 获取游戏配置模块。
4. 找到 `Configs.LevelConf.getById`。
5. 保存原始 `getById`，替换成包装函数。
6. 每次游戏请求某个主线关卡配置时，先调用原方法。
7. 当关卡 ID 满足 `2 <= id <= 150` 时，复制配置对象，并把复制对象的 `monsters` 字段设为 `[[[0]]]`。
8. 其他关卡直接返回原始配置。

因此，150 关的“跳过”发生在**客户端战斗配置读取阶段**。脚本通过给本地战斗引擎提供一个空/哨兵敌方配置，让原生战斗流程快速得到胜利或跳过敌方战斗内容；它自身没有在这个 hook 中构造 `fight_endlevel` 请求。

必须注意：以上可以直接从脚本和隔离实验确认的是“本地配置如何被改写”。是否每个当前版本的主线 `fight_startlevel` 都会再次读取这张 `LevelConf` 表，以及空怪物配置最终是否一定触发主线结算，仍需要在真实 H5 中通过被动 TGA/协议观察确认。

## 3. 混淆层还原

### 3.1 第一层 `a0D`

脚本开头的 `a0D(b, D)` 是第一层字符串解析器。其主要步骤如下：

1. 对传入表项索引做固定偏移。
2. 调用 `a0b()` 取得字符串表。
3. 首次使用时创建 Base64 字母表：

   ```text
   abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789+/=
   ```

4. 对字符串进行 Base64 风格的位重组。
5. 将字节转为 `%xx`，再调用 `decodeURIComponent`。
6. 使用传入的字符串参数作为 key，执行 RC4 风格的 KSA/PRGA XOR 解密。
7. 将结果缓存在 `a0D.yyhcMM` 中。

从结构上看，它不是标准库调用，而是一个自包含的“Base64 预处理 + RC4 风格流解密”组合。`a0D.xRbjsE` 保存了实际流解密函数，便于隔离分析时直接调用。

### 3.2 字符串表轮换

在业务代码之前有两层 `while (!![])` IIFE，反复执行：

```js
O.push(O.shift());
```

每轮会计算一串由 `parseInt` 和算术表达式构成的校验值，直到等于目标常量才停止。

第一层校验目标经过求值为：

```text
233007
```

该轮的原始调用位于约 `1695..2710`。第二层位于约 `2712..9093`，使用 `a0o()` 表。

如果只截取字符串表而不执行对应轮换，索引会落在错误位置，得到的通常是密文或乱码。因此，正确的本地分析顺序是：

```text
a0D
  -> 第一层表声明 a0b
  -> a0b 表轮换
  -> a0w/a0b/a0o 声明
  -> 第二层表轮换
  -> 业务 IIFE
```

### 3.3 第二层 `a0w`

`a0w(b, D)` 位于约 `4015865..4026897`，也是基于表项和 key 的流解密器。业务代码通过大量局部 wrapper 调用它，例如：

```js
function vL(b, D) {
  return a0D(b - 0x165, D);
}

function vS(b, D) {
  return a0D(b - offset, D);
}

function qD(PR, Pz) {
  // 根据混淆条件选择 a0w 或返回代理值
}

function oo(PR, Pz) {
  // 根据混淆条件选择 a0w 或返回代理值
}
```

`qD`、`oo`、`vL`、`vS` 的大部分条件分支是控制流平坦化或无效分支；真正的关键是它们最终把不同偏移和 key 转给 `a0D`/`a0w`。

### 5.1 对象位置和公开属性

`o3` 的完整对象表达式位于约：

```text

```


其初始状态来自前面的 `o2`：

```js

```

### 5.2 `init()` 生命周期

`o3.init()` 的可观察行为：

1. 通过 `PlatformManager` 相关环境检查。
2. 创建 style 节点和设置面板节点。
3. 读取 `localStorage["skip150_enabled"]`。
4. 将读取结果转换为 `state.enabled`。
5. 更新 checkbox、label、status 等 UI。
6. 如果读取结果启用，则调用 `applyHook()`。

用 `localStorage.getItem()` 返回字符串 `"true"` 的本地实验确认：

```text
init()
  -> state.enabled === true
  -> applyHook()
  -> hookInjected === true
  -> Configs.LevelConf.getById 被包装
```

如果存储值为空或不是启用值，则保持关闭状态，不安装关卡 hook。

### 5.3 `toggleSkip()` 生命周期

`toggleSkip()` 的核心作用是开关控制，不负责直接战斗：

```text
查找 skip150-toggle / skip150-label
  -> 读取或翻转 checkbox 状态
  -> 写入 localStorage["skip150_enabled"]
  -> 更新 state.enabled
  -> 更新 skip150-status
  -> enabled 时调用 applyHook
```

隔离实验观察到的直接存储行为：

```text
localStorage.setItem("skip150_enabled", "false")
```

开关关闭后，已有包装器仍可能保留，但包装器会因为 `state.enabled === false` 而返回原始结果，不再进行 `monsters` 改写。该实现不是通过恢复函数指针来卸载 hook。

### 5.4 `applyHook()` 的前置条件

`applyHook()` 在业务上做了以下事情：

```text
if state.hookInjected:
    return

if !state.enabled:
    return

读取 window.__require
if typeof window.__require !== "function":
    return

PlatformManager / 运行环境检查
Configs = window.__require("Configs")
LevelConf = Configs.LevelConf
if !LevelConf 或 !LevelConf.getById:
    return

保存原始 getById
安装包装函数
state.hookInjected = true
```

不同混淆分支中的常量和函数名会变化，但隔离 VM 的可观察事实稳定为：

```text
window.__require("PlatformManager")
window.__require("Configs")
Configs.LevelConf.getById
```

给 `__require` 返回最小模块桩时，观察到 `applyHook()` 的模块请求顺序为：

```text
PlatformManager
Configs
```

`PlatformManager.instance._battleVersion` 会被检查，但在本地测试中不需要真实版本值即可继续安装 hook。

### 5.5 实际包装器

包装器的混淆源码中包含大量无效分支，去除控制流噪声后，核心等价逻辑如下：

```js
const originalGetById = Configs.LevelConf.getById.bind(Configs.LevelConf);

Configs.LevelConf.getById = function getLevelConfig(levelId) {
  const originalConfig = originalGetById(levelId);

  if (!state.enabled || !originalConfig) {
    return originalConfig;
  }

  if (levelId < 2 || levelId > 150) {
    return originalConfig;
  }

  return {
    ...originalConfig,
    monsters: [[[0]]],
  };
};
```

需要特别注意三点：

1. **是浅拷贝，不是原地修改。** 原始配置对象不会被直接写入。
2. **只改 `monsters`。** 没有在这个包装器中改写 `levelId`、奖励、战斗时间、角色阵容、`outputCode` 或请求 body。
3. **使用的是 `[[[0]]]`，不是 `[]`。** 这保留了“波次 -> 敌人 -> 敌人字段数组”的层级形状，同时提供一个 ID 为 `0` 的哨兵项。

## 6. 边界和字段差分实验

### 6.1 实验方法

在本地 VM 中：

- 用一个可调用的假 `Configs.LevelConf.getById` 作为原函数。
- 原函数返回包含多个候选字段的配置对象。
- 让 `window.__require("Configs")` 返回 `PlatformManager` 和 `Configs` 桩。
- 设置 `o3.state.enabled = true`。
- 执行 `o3.applyHook()`。
- 调用包装后的 `getById()`，比较返回值和原始值。

实验没有真实游戏模块、网络、BIN 或服务器。

### 6.2 数字边界结果

| 输入 ID | `monsters` 结果 | 是否改写 |
| ---: | --- | --- |
| `-1` | 原值 | 否 |
| `0` | 原值 | 否 |
| `1` | 原值 | 否 |
| `1.5` | 原值 | 否 |
| `1.9` | 原值 | 否 |
| `2` | `[[[0]]]` | 是 |
| `2.1` | `[[[0]]]` | 是 |
| `149` | `[[[0]]]` | 是 |
| `150` | `[[[0]]]` | 是 |
| `150.1` | 原值 | 否 |
| `151` | 原值 | 否 |
| `300` | 原值 | 否 |

由此可复核的数值条件是：

```text

```

源码没有额外的 `Number.isInteger()` 检查，因此小数 `2.1` 在 JavaScript 比较语义下也会命中；这不是“整数关卡列表”的严格判断，而是普通数值比较。

### 6.3 字符串和特殊值

实验还观察到：

| 输入 | 结果 |
| --- | --- |
| `"2"` | 命中 |
| `"150"` | 命中 |
| `"150.1"` | 不命中 |
| `null` | 不命中 |
| `undefined` | 不命中 |

原因是 `"2" < 2`、`"2" > 150` 会发生 JavaScript 数字转换，而 `null`/`undefined` 在边界比较中不会形成命中条件。


对命中对象最终可见的字段变化只有：

## 7. 配置结构和“为什么可能能跳过战斗”

### 7.1 `LevelConf` 的数据结构

仓库中的游戏协议/配置模型显示，`LevelConf` 是一个带 `list` 和 `map` 的静态配置表：

```js
LevelConf.getById = function (id) {
  return LevelConf.map.get(id);
};
```

配置解码时，服务器或资源数据会被复制到配置实例并放入 Map。参考：[source/4.js](../../source/4.js) 中的 `LevelConf` 定义。

因此，`7.7.12.js` 并没有修改 Map 中原始实例，而是在查找返回后复制一份对象并替换其 `monsters` 属性。

### 7.2 `monsters` 的形状

从仓库内战斗/配置辅助代码可以看到，敌方配置通常以多层结构表达：

```text
monsters
  -> 多个波次
      -> 多个敌人
          -> [monsterId, index/type, level]
```

已有模拟代码会把这样的配置归一化为敌方怪物条目；因此：

```js
[[[0]]]
```

仍然是一个三层数组，而不是完全破坏数组类型。最内层的 `0` 看起来是无效/空怪物 ID。

### 7.3 可确认和不可确认的部分

**可以确认：**

- 游戏读取 2 到 150 关配置时，会看到 `monsters = [[[0]]]`。
- 原始关卡配置的其他字段保持不变。
- 该行为是客户端本地 hook。

**暂时不能仅凭该脚本确认：**

- 当前版本 `fight_startlevel` 是否在服务器下发 battleData 后再次调用 `LevelConf.getById()`。
- 空怪物是否由官方战斗引擎解释为立即胜利、跳过敌方波次，还是走某个异常/空战斗分支。
- 服务器是否只接受客户端真实战斗结果，或该功能对应的是另一套本地梦境/副本玩法。

## 9. 与仓库 pushLevel 方案的边界

仓库当前主线 pushLevel 研究记录在：

- [docs/mainline-pushlevel-protocol-research.md](../mainline-pushlevel-protocol-research.md)
- [docs/mainline-pushlevel-implementation-plan.md](../mainline-pushlevel-implementation-plan.md)
- [docs/pushlevel-tolerance-experiment-20260903.md](../pushlevel-tolerance-experiment-20260903.md)

仓库方案的协议链是：

```text
fight_startlevel({})
  -> Fight_StartLevelResp / battleData
  -> 本地官方引擎或结果生成器
  -> fight_endlevel({ levelId, battleTime, tapTimes, autoTapTimes, outputCode, log })
```

而 `skip150` 的链是：

```text
游戏初始化
  -> 读取 localStorage 开关
  -> __require("Configs")
  -> 包装 LevelConf.getById
  -> 游戏后续读取 level config 时看到空怪物哨兵
```

两者的控制面不同：

| 维度 | `skip150` | 仓库 pushLevel |
| --- | --- | --- |
| 运行位置 | 注入脚本/H5 客户端运行时 | Vue/WS/BON 或官方 iframe |
| 核心入口 | `Configs.LevelConf.getById` | `fight_startlevel` / `fight_endlevel` |
| 主要改动 | 本地 `monsters` 配置 | 构造/提交战斗结果 |
| 是否直接发 endLevel | 未发现 | 是目标协议路径 |
| 是否依赖 `outputCode` | 未发现 | 依赖 |
| 是否修改服务器关卡状态 | 脚本本身没有直接做 | 由服务器响应决定 |
| 是否能处理 151+ | hook 不处理 | 由正常主线方案处理 |

不要把 `skip150` 的成功机制直接移植为 Vue 侧 `fight_endlevel` payload。它依赖游戏 H5 内部的配置访问和原生战斗流程；在普通 helper WebSocket 连接中没有 `LevelConf` 对象。

## 10. 与已有主线协议证据的关系

当前项目已有的主线协议事实：

- `fight_startlevel` 请求体为空对象。
- 服务端下发完整 `battleData`，包括 `randomSeed`、双方阵容和 `options.levelId`。
- 官方客户端会本地生成战斗结果。
- `fight_endlevel` 提交 `battleTime`、`tapTimes`、`autoTapTimes`、`outputCode` 等字段。
- 官方无头引擎可以生成与 `outputCode` 公式一致的战斗结果。

这些事实并不自动说明 `skip150` 参与了主线协议，因为：

1. 服务器下发的 `battleData.rightTeam` 可能已经包含敌方阵容。
2. 服务器流程可能不再查本地 `LevelConf`。
3. `LevelConf` 可能只被某个本地战斗/梦境模块使用。
4. `skip150` 可能是为另一种“本地推关”或旧版本流程设计的兼容 hook。

因此当前正确的证据表述是：

```text
[直接确认]
skip150 修改本地 LevelConf.getById() 的 monsters。

[高置信推断]
目标是让 2..150 关的本地敌方配置为空，从而加速或跳过本地战斗。

[待验证]
该改写是否影响当前版本主线 fight_startlevel 的战斗结算，以及是否能真实推进服务器关卡。
```

## 12. 后续真实 H5 被动验证建议

不需要主动发送未知请求，也不需要先启用自动推关。建议使用现有研究桥的被动模式，用户手动完成一场能安全观察的战斗，重点采集：

1. `Configs.LevelConf.getById(2).monsters`。
2. `Configs.LevelConf.getById(150).monsters`。
3. `Configs.LevelConf.getById(151).monsters`。
4. 触发主线战斗时是否调用 `getById`。
5. `c_battleLevelStart` 中的 `level`、`randomSeed`、敌方阵容摘要。
6. `c_battleSuccess`/`c_battleFail` 与 `fight_endlevel` 的对应关系。
7. 服务端下发的 `battleData.rightTeam` 是否仍然拥有有效敌方成员。

需要区分两种观察结果：

### 情况 A：主线战斗仍读取 `LevelConf`

这支持以下高置信解释：

```text
skip150 hook
  -> 主线本地关卡配置为空
  -> 原生引擎跳过/快速胜利
  -> 官方流程照常生成和提交结果
```

仍需通过 TGA 和服务器响应确认是否真正推进。

### 情况 B：主线战斗只使用服务端 `battleData`

则 `skip150` 可能只影响：

- 本地旧版关卡流程。
- 梦境/副本/其他使用 `LevelConf` 的战斗。
- UI 预览或本地缓存。

此时它不能直接解释当前主线 pushLevel 的结果。

## 13. 安全和数据处理注意事项

1. 不要把真实 Token、BIN、`encryptCombUser`、完整角色对象或未脱敏日志写入本文或仓库。
2. `skip150` 是客户端注入 hook，不应被描述为服务器漏洞或保证能推进关卡。
3. 不要因为配置 hook 存在，就在真实账号上盲发 `fight_endlevel`。
4. 研究桥继续保持 `passive-capture`；主动战斗和提交应保持独立的 test-only 入口。
5. 任何真实验证都应一次只观察/提交一场，并记录请求前后关卡、响应 code 和 TGA 结果。
6. 关闭开关不一定卸载函数包装器；在页面生命周期内应重新加载或显式恢复原函数才能确保完全清理。

## 14. 交接摘要

后续接手者只需要记住以下事实：

```text
7.7.12.js
  -> o3
  -> skip150_enabled
  -> window.__require("Configs")
  -> Configs.LevelConf.getById
  -> 2 <= levelId <= 150
  -> shallow copy
  -> monsters = [[[0]]]
```

这是一条**本地关卡配置注入链**，不是：

```text
fight_startlevel
  -> 手工构造 ClientBattleResult
  -> fight_endlevel
```

后续若要证明它确实能推动当前主线服务器，最小证据不是继续猜混淆变量，而是一次被动 H5 观察：确认主线战斗是否读取被 hook 的 `LevelConf`，并比较 `battleData.rightTeam`、TGA 结果和正常 endLevel 响应。
